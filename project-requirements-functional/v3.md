# Nami — Functional Requirements Document (v3)

**Project:** Nami Personal Finance Assistant  
**Owner:** Personal use  
**Version:** 3.0  
**Date:** 2026-05-24

---

## 1. Overview

Nami v3 extends the message ingestion pipeline and database structure. When an external SMS ingestion client (like iOS Shortcuts) has additional context (such as the category or the mode of payment), it can POST these fields directly. These fields propagate through the database to transactions and are rendered and editable inline on the dashboard ledger.

---

## 2. Updated System Flows

### 2.1 Rich Message Ingest Flow
1. The ingestion client POSTs a JSON payload to `/api/messages` or `/messages` containing:
   - `message` (required, raw SMS string)
   - `category` (optional, string)
   - `modeOfPayment` (optional, string)
2. The backend validates and inserts these fields into `raw_messages` columns: `message`, `category`, and `mode_of_payment`.

### 2.2 Rich Transaction Processing Flow
1. When the transaction generator parser runs (via cron or manual reprocessing):
   - It extracts the amount from the raw message text.
   - It creates (or updates) a `transactions` record containing:
     - `amount`: parsed value
     - `category`: pre-populated with the raw message `category` if it exists and is valid (else `null`)
     - `mode_of_payment`: pre-populated with the raw message `mode_of_payment` if it exists (else `null`).

### 2.3 Ledger Management Flow
1. User views the transaction list on the dashboard.
2. The user can see the category pill and the **Mode of Payment** pill.
3. If the payment mode is empty or null, it shows `Select Mode` (or similar muted badge).
4. User can click the payment mode badge to trigger an inline select menu to set or change it (UPI, Card, Cash, Net Banking, or clear it).
5. Updates save immediately to the backend via `PATCH /api/transactions/{id}`.

## 3. Functional Requirements

### 3.1 Ingestion API Enhancements

| ID | Requirement |
|---|---|
| FR-43 | Ingestion API SHALL accept optional `category` and `modeOfPayment` fields in JSON payloads |
| FR-44 | System SHALL store custom category and mode of payment in `raw_messages` table |

### 3.2 Processing Engine Enhancements

| ID | Requirement |
|---|---|
| FR-45 | Transaction generator SHALL copy the ingested `category` (if valid) and `mode_of_payment` to the transaction record upon successful parsing |
| FR-46 | If the custom category is invalid or missing, transaction category SHALL default to `null` |
| FR-47 | If the custom mode of payment is missing, transaction mode of payment SHALL default to `null` |

### 3.3 Dashboard & Transaction API Enhancements

| ID | Requirement |
|---|---|
| FR-48 | `GET /api/transactions` SHALL return the `mode_of_payment` field for each transaction |
| FR-49 | `PATCH /api/transactions/{id}` SHALL allow updating the `mode_of_payment` field |
| FR-50 | Transaction list UI SHALL render the mode of payment badge inline for each transaction |
| FR-51 | Transaction list UI SHALL provide an inline picker to modify the mode of payment (UPI, Card, Cash, Net Banking, None) |
