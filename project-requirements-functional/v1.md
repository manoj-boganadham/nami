# Nami — Functional Requirements Document

**Project:** Nami Personal Finance Assistant  
**Owner:** Personal use  
**Version:** 1.0  
**Date:** 2026-05-24

---

## 1. Overview

Nami is a personal finance tracking system that captures debit/spend SMS messages from an iPhone, processes them into structured transactions, and presents spending analytics via a web dashboard. The user can categorize transactions from the dashboard or via notification reply.

---

## 2. Stakeholders

| Stakeholder | Role |
|---|---|
| Owner / User | Single end-user. Defines requirements, uses the product daily. |
| Coding Agent | Implements the system based on this document. |

## 3. System Flows

### 3.1 Message Ingest Flow

**Trigger:** User receives a debit/spend SMS on iPhone. An iOS automation (Shortcuts app) fires on message receipt and POSTs the message contents to the API.

**Steps:**
1. iPhone Shortcuts automation detects a new SMS
2. Automation sends an HTTP POST to `/api/messages` with the raw message text
3. API receives the message, attaches a UTC timestamp, and saves it to the `raw_messages` table
4. API responds with `201 Created` and the saved record

**Outcome:** Raw message stored in the database, unprocessed.

---

### 3.2 Transaction Generation Flow

**Trigger:** A cron job runs once daily (configurable time, e.g. 11:00 PM).

**Steps:**
1. Cron invokes `generate_transactions.py`
2. Script queries all `raw_messages` where `processed = false`
3. For each message:
   - Run regex extraction to parse the amount (INR)
   - If amount found: create a record in `transactions` table with `amount`, `raw_message_id`, `timestamp` (from raw message), `category = null`
   - If amount not found: mark message as `processed = true`, `parse_failed = true` and skip
4. Mark processed messages as `processed = true`

**Outcome:** Structured transaction records created. Category is null until user assigns one.

---

### 3.3 Categorization Flow

User can categorize a transaction in two ways:

**3.3.1 From Dashboard**
1. User opens dashboard, sees uncategorized transactions highlighted
2. User taps/clicks a transaction row
3. A category picker appears (Food, Transport, Shopping, Health, Utilities, Entertainment, Other)
4. User selects a category → saved immediately via `PATCH /api/transactions/:id`

**3.3.2 Via Notification Reply**
1. When a new transaction is generated, the system sends a notification (push or Telegram/WhatsApp message) with the transaction details and a list of category options
2. User replies with a number or category name
3. System receives the reply and updates the transaction category via the same `PATCH` endpoint

---

### 3.4 Dashboard Flow

**Trigger:** User opens the web dashboard in a browser.

**Steps:**
1. Dashboard loads with default view: today's transactions
2. User can select a date range using presets or a custom picker
3. Dashboard fetches data from the API and renders:
   - Total spend for the selected range
   - Category-wise breakdown (bar or donut chart)
   - Daily spend trend (bar chart over selected range)
   - Transaction list (grouped by day)
   - Flagged transactions (above configurable threshold, default ₹2,000)
4. User can tap a transaction to categorize it inline

## 4. Functional Requirements

### 4.1 Message Ingest API

| ID | Requirement |
|---|---|
| FR-01 | System SHALL expose a `POST /api/messages` endpoint |
| FR-02 | Endpoint SHALL accept a plain-text or JSON body containing the raw message string |
| FR-03 | System SHALL store the raw message with a UTC timestamp on receipt |
| FR-04 | System SHALL return `201 Created` with the saved record on success |
| FR-05 | System SHALL return `400 Bad Request` if the message body is empty |
| FR-06 | Endpoint SHALL be secured with a static API key passed in the request header (`X-API-Key`) |

---

### 4.2 Transaction Generation (Cron Job)

| ID | Requirement |
|---|---|
| FR-07 | System SHALL provide a standalone script `generate_transactions.py` invokable by cron |
| FR-08 | Script SHALL process only unprocessed raw messages (`processed = false`) |
| FR-09 | Script SHALL extract the INR amount from the message using regex |
| FR-10 | Script SHALL support amount formats: `₹500`, `Rs 500`, `Rs. 1,200`, `500 rupees`, `paid 300`, `spent 450` |
| FR-11 | On successful extraction, script SHALL create a transaction record with `amount`, `raw_message_id`, `timestamp`, `category = null` |
| FR-12 | On failed extraction, script SHALL mark the raw message as `parse_failed = true` and skip transaction creation |
| FR-13 | Script SHALL mark all attempted messages as `processed = true` after processing |
| FR-14 | Cron schedule SHALL be configurable via `.env` (default: `0 23 * * *`) |

---

### 4.3 Categorization

| ID | Requirement |
|---|---|
| FR-15 | System SHALL expose a `PATCH /api/transactions/:id` endpoint to update category |
| FR-16 | Valid categories SHALL be: Food, Transport, Shopping, Health, Utilities, Entertainment, Other |
| FR-17 | Dashboard SHALL visually distinguish uncategorized transactions (e.g. muted row + tag) |
| FR-18 | Dashboard SHALL provide an inline category picker on transaction row tap/click |
| FR-19 | System SHALL support notification-based categorization via Telegram Bot or WhatsApp (nice-to-have) |
| FR-20 | Notification SHALL include transaction amount, raw message snippet, and numbered category options |

---

### 4.4 Dashboard

| ID | Requirement |
|---|---|
| FR-21 | Dashboard SHALL load with a default view of today's transactions |
| FR-22 | Dashboard SHALL provide date range presets: Today, Last 7 Days, Last 30 Days, Custom |
| FR-23 | Dashboard SHALL display total spend for the selected range |
| FR-24 | Dashboard SHALL display category-wise spend breakdown as a chart |
| FR-25 | Dashboard SHALL display a daily spend trend chart over the selected range |
| FR-26 | Dashboard SHALL list all transactions grouped by day, showing amount, description, category |
| FR-27 | Dashboard SHALL flag and highlight transactions above the configured threshold |
| FR-28 | Dashboard SHALL support light and dark themes with a toggle in the header |
| FR-29 | Theme preference SHALL persist in `localStorage` |
| FR-30 | Dashboard SHALL show count of uncategorized transactions as a prompt to the user |

---

## 5. Non-Functional Requirements

| ID | Requirement |
|---|---|
| NFR-01 | Stack: Python 3.11+, FastAPI, SQLite, vanilla JS or React frontend |
| NFR-02 | Ingest API response time SHALL be under 300ms |
| NFR-03 | All times stored in UTC; displayed in local time on the dashboard |
| NFR-04 | The API key for ingest SHALL be stored in `.env`, never hardcoded |
| NFR-05 | The system is intended for single-user, local/private network deployment |

## 6. Database Schema

### `raw_messages`
| Column | Type | Notes |
|---|---|---|
| id | INTEGER | PK, autoincrement |
| message | TEXT | Raw SMS content |
| received_at | DATETIME | UTC, set on insert |
| processed | BOOLEAN | Default false |
| parse_failed | BOOLEAN | Default false |

### `transactions`
| Column | Type | Notes |
|---|---|---|
| id | INTEGER | PK, autoincrement |
| raw_message_id | INTEGER | FK → raw_messages.id |
| amount | REAL | Extracted INR amount |
| category | TEXT | Null until user assigns |
| timestamp | DATETIME | Copied from raw_message.received_at |
| created_at | DATETIME | UTC, set on insert |

---

## 7. API Endpoints Summary

| Method | Endpoint | Description |
|---|---|---|
| POST | `/api/messages` | Ingest raw SMS message |
| GET | `/api/transactions` | List transactions (supports `?date=`, `?from=&to=`) |
| PATCH | `/api/transactions/:id` | Update transaction category |
| GET | `/api/stats` | Aggregated stats for a date range |
| GET | `/dashboard` | Serve the web dashboard |

---

## 8. Out of Scope

- AI-based auto-categorization (user assigns manually)
- Multi-user support or authentication beyond API key
- Budget limits or savings goals (future)
- iOS app — automation via iPhone Shortcuts only
